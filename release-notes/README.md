# リリースノートの書き方

`package.json` の `version` を上げるときは、同じ PR で `release-notes/v<version>.md` を書きます。
main へのマージでリリースされるとき、このファイルの内容がリリースページの本文の先頭に入ります
（その後ろに、インストール時の注意と、GitHub が自動生成する PR 一覧が続きます）。

ファイルが無い・書式が崩れている場合は、PR の CI（Build）とリリースの両方が失敗します
（`node scripts/check-release-notes.mjs` で手元でも確認できます）。

## 書式

```markdown
**このリリースの要点を 1〜2 文で。**

## ✨ 新機能

### 機能名
何ができるようになったか・どんな場面で役立つかを 1〜3 文で。

- 具体的にできること / 操作方法
- …

→ 詳しくは [ヘルプ: 章名](https://yyamada722.github.io/constella/guide/xxx)

## 🛠 改善

- 既存機能の使い勝手の変化。「〜できるようになりました」「〜が見やすくなりました」

## 🐞 修正

- 何がおかしかったか、どう直ったか（利用者から見た症状で書く）

## ⚠️ ご注意

- データ形式の変更、挙動の変更、手動で必要な操作など。無ければ節ごと省略
```

- 1 行目は **太字の要約**（リリース一覧や通知で最初に目に入る部分）。
- `##` 見出しは上の 4 つだけ・この順で使う。該当が無い節は省略してよい。
- 利用者目線で書く。内部の型名・関数名・reducer・IPC などの実装用語は出さない
  （PR 本文やコミットメッセージに書く）。
- 操作はアプリ上の表記どおりに書く（例:「設定 → コマンドライン (CLI)」「Ctrl+Z」）。
- 新機能にはヘルプ / ドキュメントサイトへのリンクを付ける。
- `TODO` などの書きかけを残さない。
